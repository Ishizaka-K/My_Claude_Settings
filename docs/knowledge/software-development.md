# 一般的なソフトウェア開発の普遍知識

## 基本原則

- 変更は小さく、目的を明確にする。
- 責務の境界を保つ。
- 依存方向を意識し、詳細が方針を支配しないようにする。
- 読みやすさは、短さよりも意図の明確さで判断する。
- テストしやすい構造は、保守しやすい構造であることが多い。

## 設計

- 要件、非目標、制約、前提を分ける。
- ドメインの言葉をコード構造に反映する。
- UI、アプリケーションロジック、ドメイン、インフラを混ぜすぎない。
- 外部 API、DB、ファイル、時刻、乱数、ネットワークは境界として扱う。
- 将来の拡張を理由に抽象化しすぎない。実際に変化しそうな軸だけ分離する。

## 実装

- 既存の規約、命名、ディレクトリ構成を優先する。
- 関数やクラスは、1つの理由で変更される単位に近づける。
- エラーは握りつぶさず、呼び出し元が判断できる形にする。
- ログには原因調査に必要な情報を入れるが、秘密情報は出さない。
- 設定値、シークレット、環境依存値をコードに埋め込まない。

## テスト

- 重要な分岐、境界値、失敗経路を優先する。
- ドメインロジックは単体テストしやすく保つ。
- 外部 I/O は境界で差し替えられるようにする。
- テスト名は仕様として読める名前にする。
- 壊れやすい UI や時刻依存のテストは、安定化の工夫を入れる。

## レビュー

- 仕様違反、データ破壊、セキュリティ、競合、例外経路を優先して見る。
- 好みの違いと実害のある問題を分ける。
- 指摘には、根拠、影響、修正案を含める。
- High は、正しさや安全性が保証できない問題に限定する。
