# ブログ執筆の普遍知識

## 目的

ブログ記事は、読者が「読んでよかった」と感じる具体的な変化を作るために書く。知識の羅列ではなく、読者の疑問、判断、実装、失敗回避を助ける構造にする。

## 読者設計

- 読者の現在地を決める。初心者、実務経験者、特定技術の経験者では必要な前提が違う。
- 読者が記事を開いた理由を1つに絞る。
- 読後にできるようになることを明確にする。
- 想定読者が知らない言葉は、最初に短く定義する。

## 記事構成

基本構成は次を使う。

```md
# タイトル

## はじめに
この記事で解決すること、対象読者、前提。

## 背景
なぜこの問題が起きるのか。

## 結論
先に要点を示す。

## 本文
手順、考え方、実装例、比較。

## つまずきポイント
読者が失敗しやすい箇所。

## まとめ
持ち帰るべき判断基準。
```

## タイトル

- 読者が検索する言葉を含める。
- 抽象的な言葉だけで終わらせない。
- 「何を」「どうできるようになるか」を入れる。
- 誇張しない。記事内容とタイトルの約束を一致させる。

## 本文の書き方

- 結論を先に書き、理由と具体例を後に置く。
- コード例の前に、何を示すコードなのかを一文で説明する。
- 手順記事では、コマンド、期待される出力、失敗時の確認箇所を分ける。
- 比較記事では、勝ち負けではなく適用条件を書く。
- 意見を書く場合は、事実、推論、好みを分ける。

## 技術記事の品質

- 動作確認した環境を書く。
- バージョン依存の内容はバージョンを書く。
- 公式ドキュメント、一次情報、実際のエラーメッセージを優先する。
- コードは最小だが実用に近い形にする。
- セキュリティ、認証情報、課金、データ削除に関わる箇所は注意書きを入れる。

## レビュー観点

- タイトルと本文の約束が一致しているか。
- 読者の前提が置き去りになっていないか。
- 結論が遅すぎないか。
- コードが再現可能か。
- 抽象論だけで、読者の次の行動に落ちていない箇所がないか。
